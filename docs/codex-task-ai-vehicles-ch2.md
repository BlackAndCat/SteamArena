## 4. 每关的五台设计流程

先提出五个战术和布局上确实不同的概念，说明参考来源、主战术、车体轮廓和奖励模块的用途。
五台不能仅靠改名称、材料颜色或升级等级凑数。
在概念通过主线程范围检查后，Sol 直接编写各车完整 `cells`。

以下是待 Sol 根据十辆参考细化的设计侧重点，不是锁定配置或指定模块组合：

| 关卡 | 五种设计侧重点 |
|---|---|
| 烟囱 | 紧凑核心保护、低矮稳固轮廓、前部接敌控制、侧向火力协同、持续输出与冷却搭配 |
| 走锭机 | 双足重心平衡、紧凑躯干保护、移动射击协同、冷热负载平衡、接近与脱离节奏 |
| 绞盘 | 牵引后接续输出、远近武器分工、坡地稳定轮廓、机动牵制、牵引与核心防护平衡 |

Sol 可在分析后调整这些侧重点，须解释搭配依据，并保持五台的战术和布局有实质区别。

每台车应能用几句话回答：

1. 为什么采用这个底盘与车体比例？如何避免明显悬挑、比例失衡和零散堆叠？
2. 主武器、辅助件、供能冷却如何搭配？核心如何保护？
3. 本关必装模块在战术中起什么作用，而不是单纯挂上去满足条件？
4. 对上一关参考车预期怎样交战？主要弱点是什么？

Sol 可以依据校验、真实预览和战斗结果作有目的的直接修订。
修订应说明问题、改动和结果，保留设计骨架，避免为了单个成绩破坏整车搭配。
建议每台先安排少量诊断测试，再进行正式测试；若持续失效，可重新设计该候选。

禁止使用以下入口产车，包括以它们作自动保底或预算填充：

`randomVehicle`、`requiredVehicle`、`minimalVehicle`、`mutate`、`approachBudget`、
`initialPopulation`、`nextPopulation`、`generateChapter`、`run`、`runAsync`、`runParallel`。
也不调用会自动探测策略的 `evaluateCandidate`，直接使用指定策略的 `simulate`。

不执行随机造车、突变、交叉、种群搜索或自动预算补装。
现有工具里的规则读取和校验函数可以复用，它们本身不代表执行进化。

## 6. 实战与实际预览

直接用 `SA.Battle.simulate` 测试，不用进化入口挑选或改装车辆。
建议每台正式测试 60 对种子，双方换边，共 120 局；所有候选使用可复现的种子安排。
记录场地、双方策略、参考车辆、种子、胜负、伤害、开火情况与常见失效。
若现有接口不能提供某项诊断，注明缺失，不能猜测或编造。

保留对上关参考车 60%～75% 的现有胜率目标。
低于 45% 必须明显标记未达标，并解释常见原因；超出目标上界同样如实标记。
硬规则合法但实战未达目标的候选仍可交付，成绩必须真实可见。
强度 90%＋节约 10%、预算缺口指数扣分、低于 45% 的胜率扣分可作为报告参考。
它们不能替代实战记录，也不用于调用算法自动选配。

每台最终车都要看真实游戏渲染图，检查整车比例、轮廓、模块关系与明显布局问题。
预览使用最终 `cells`，不美化截图，不替换游戏画面，不通过改美术掩盖构筑问题。
渲染观感和战力分别记录；不能把“合法”或“预算用满”写成“好看且能打”。

## 7. 串行参考链与推荐规则

推荐依据包含合法性、实战、整体搭配，记录候选 ID、选择理由与 `cells` 指纹。

走锭机以烟囱临时参考为主对手；绞盘以走锭机临时参考为主对手。
后关同时对前关其余四台做少量交叉检查，避免只克制单一布局；记录测试规模与结果。
不需要逐关等待用户选车才能继续，但临时参考必须由主线程／Astra 按本蓝图验收并明确确认。
如前关没有战力合格的代表，应明确标记“弱参考”并说明后关成绩的局限。
不能把对弱参考的高胜率，或对正常参考的 0% 胜率写成达标。

临时参考不是正式关卡采用。用户后续改选时，重验受影响的后续车辆。
