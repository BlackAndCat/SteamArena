# 关卡车进化生成器 · 规则与开发计划书

> 2026-09-25 · v1。负责：astra（后台）。先读 `docs/collab.md`。
> 本文件记录用户已经拍板的算法规则和开发顺序。标"暂定"的数值 astra 可以按实测提议修改；标"已定"的只有用户能改。

## 0. 目标

用一套可以反复重跑的离线算法，自动生成战役各关（含 Boss）的对手车，替换现有的关卡车。同时把每一档表现优秀的车存成候选车库，供用户以后手工设计时参考（手工设计不是算法的工作）。

玩家应该感受到的效果：

1. **难度平滑上升**：从序章到女王号，对手强度连续递增。
2. **敌人真的强**：对手输是因为被打败，而不是自己热死或拖到超时。
3. **每场都是不同的构筑题**：近战撞击、直射远程、高抛、升温、牵引等打法都有；地形关的对手在自己的主场特别难缠。
4. **Boss 是本档的标杆**：它代表这一档构筑得好的车，玩家要造出同等水平的车才打得过。
5. **对手和玩家的进度对得上**：对手只用那一关前后能拿到的东西；给模块奖励的对手，车上就装着那件模块。
6. **比赛好看**：命中、近身肉搏、利用地形的打法比拖死、热死、远程磨血更受青睐。

**不做**：关卡名、剧情描述、"看得见的弱点"，以及最终的难度校准。这些由用户手工完成。

## 1. 已定的参数（用户决定）

| 项 | 决定 |
|---|---|
| 超时判定 | 时间到时，双方按"造成的伤害（占对手总耐久的比例）× 60% + 自己剩余耐久比例 × 40%"比较，高者胜。用来增加进攻的收益 |
| 表现分权重 | 先用 §4 的默认权重，跑出结果后用户再调 |
| **Boss 就是参考车** | 每一档的 Boss 就是这一档的标杆和参考车。Boss 是通用型的：不是地形特化车，也不是毒瘤车或奇特构筑；它对本档种群的平均胜率不低于 50%（携带下一档新模块的奖励车除外）。反过来说，用本档配置的玩家打 Boss，胜率不高于 50% |
| 奖励车强度 | 带模块奖励的普通关对手：**打低一档参考车（上一档 Boss）的胜率不低于 60%**，也就是用低一档配置的玩家打它，胜率不高于 40%；**防碾压上限**：上一档 Boss 打它的胜率不低于 15%。奖励模块必须过"生效门槛"（§7.6） |
| 分档粒度 | 按章进化，按关选车（每一关单独检查它的解锁、改装台大小、材料上限和预算） |
| 多样性 | 必须保留：近战、远程、抛射等打法都要有；表现偏离常规但能打的极端构筑也要保留 |
| AI 性格 | 由车型决定：每台车绑定最适合它的性格，这本身就是一种多样性 |
| 毒瘤车 | 强度分很高、表现分很低的车单独保留，结束后要能看到它的样子 |
| 战斗规则冻结点 | 大的战斗机制改动做完之前，只跑系统健康测试和快速评估，不做正式生成（§10.5） |
| 存储 | 记录不能塞满硬盘，按 §12 的上限执行 |

## 2. 总体结构

```
关卡规格（设计意图，权威）
      │
系统健康测试 ──► 调好热量、水箱、时长等数值（用户批准）
      │
进化生成器：按章分档 → 种群 → 对战评估（强度分 + 表现分 + 特征）→ 分类存档 → 放宽约束进入下一档
      │
选关：按关卡规格从存档里挑车 → 导出到 content.js
      │
报告页：分类网格、散点图、毒瘤车、奇特构筑、复现和试驾
      │
规则变化：规则指纹 → 复核 → 影响报告 → 只重跑偏移超标的部分
```

## 3. 基础设施

1. **Node 无界面运行**：在 Node 里加载游戏脚本，调用 `SA.Battle.simulate()`，不依赖浏览器页面。和 `docs/collab.md` §8 的任务 F（自动化检查）共用同一套运行环境。
2. **多进程并行**：用 worker 按 CPU 核数并行对局。
3. **可固定种子的随机数**：战斗里所有 `Math.random()` 改成走一个可以设种子的随机数生成器（游戏里照常用随机种子）。任何一局都能凭"车 + 对手 + 地形 + 种子"原样复现。
4. **战斗事件记录**：`simulate()` 返回每一方的统计，供 §4 和 §5 使用：
   - 开火、命中、蓄满后命中；
   - 撞击次数、击退、推进泥地；
   - 被地形挡下的敌弹、居高命中、下坡冲撞；
   - 两车距离的时间分布、不交战时间；
   - 击毁的模块，结局类型，逆转；
   - 热量和水的曲线摘要。
5. **规则指纹**：把 `SA.MODULES`、`SA.K`、`SA.TERRAINS` 和 `battle.js` 里一个手动维护的 `SA.RULES_VERSION` 合成一个哈希。每台车、每份报告、每次导出都带上它。
6. **超时判定改成 §1 的 60 / 40 规则**：属于战斗规则修改，在这一阶段完成，并同步 `README.md` 的胜负说明。

## 4. 表现分（观众算法）

每一局给双方各打 0～100 分，一台车的表现分是它所有对局的平均值。所有权重写在配置文件 `tools/evolve-config.js` 里，用户可以直接改。

**默认权重（暂定）**：基础 40 分，加减后截断到 0～100。

| 项 | 计算 | 分值 |
|---|---|---|
| 命中率 | 命中 / 开火 | 最多 +12 |
| 精准命中 | 蓄满后命中占全部命中的比例 | 最多 +5 |
| 近身交战 | 两车车头距离 < 200px 的时间占比 | 最多 +12 |
| 撞击 | 有效撞击、击退、把对手推进泥地的次数（封顶） | 最多 +8 |
| 利用地形 | 被坡 / 货箱挡下的敌弹、居高命中、下坡冲撞、鱼叉拉人（封顶） | 最多 +8 |
| 拆解 | 击毁的敌方模块数（封顶） | 最多 +8 |
| 干净利落 | 以驾驶舱全毁或对手投降结束 | +10 |
| 节奏 | 用时在 30～60 秒得满分，越偏离越少 | 最多 +7 |
| 逆转 | 曾经落后 30% 以上耐久比例，最后获胜 | +5 |
| 热死 | 自己烧干停机 / 靠对手烧干获胜 | −20 / −12 |
| 超时、平局 | 按超时判定结束 / 平局 | −8 / −10 |
| 远程磨血 | 两车距离 > 500px 而且这段时间伤害效率低的时间占比 | 最多 −20 |
| 不交战 | 双方都没有开火、没有接触的时间占比 | 最多 −10 |

放风筝不会一刀切：远距离但命中率高、打得出伤害的车，照样能拿高分；只罚"拉远了又打不出伤害"。

## 5. 强度分

- **做法**：让每台车和一组**标尺车**在指定地形上对打，平局算半场，用所有对局结果拟合一个天梯分（Bradley–Terry / Elo 类），带 95% 置信区间。
- **分地形计算**：每台车至少有"平地"和"它可能擅长的地形"两份强度分。
- **标尺车**：
  - **本档和上一档的 Boss**（§7.7）。Boss 就是参考车，"本章参考车""低一档参考车"分别指本档 Boss 和上一档 Boss；
  - 再加本档种群里各格的代表车，用来让分数更稳定。
  - 第一档（序章）还没有上一档：用序章开局车作为起点标尺。
- **局数**：进化过程中可以少打（每对 6～10 局）；进存档和选关时，每对至少 40 局。
- 现有的评分公式（`stats().rating`）只作初筛参考，不用于最终判断。

## 6. 系统健康测试（进化之前先做）

目的：确认战斗规则本身不鼓励堆水箱、拖时间、等对手热死。

| 测试 | 做法 | 合格线（暂定） |
|---|---|---|
| 结局分布 | 一组各类型的标准车大量互打 | 烧干 < 30%，超时 < 10%，平局 < 5%，平均时长 30～60 秒 |
| 水箱边际价值 | 标准车把 0～4 格装甲或武器依次换成水箱，看胜率曲线 | 第 1～2 个水箱有明显收益，之后变平或下降 |
| 拖延收益 | 纯龟缩加堆水、纯风筝加堆水的车，对打正常配置 | 胜率不超过 50% |
| 升温武器 | 喷火器 / 蒸汽喷射器对打正常冷却的车 | 不能单靠升温在 25 秒内致胜 |
| 表现分分布 | 标准车互打的表现分 | 正常构筑集中在 40～70 分，没有大面积 0 分或满分 |

**参数搜索**：
- 把热量和时长相关的常数当成参数：待机产热、散热、冷却曲线、每点热量耗水、水箱容量、开火产热、战斗时长。
- 在给定范围内搜索，让上表各项同时接近合格线。
- 输出推荐数值、每个参数的敏感度，以及改前和改后的对比。
- **改不改由用户批准**，astra 不自行提交数值改动。

## 7. 进化生成器

### 7.1 分档与约束

- **每一章是一档。** 每档的约束从 `SA.CAMP_START` 和 `SA.CAMPAIGN` 的解锁数据推出来：可用模块、材料上限、改装台大小、预算（按经济轨迹）。
- **Boss 和奖励车可以超出本档约束**：Boss 可以带个别史诗件（和现在关卡里的 `elite` 一样）；奖励车必须带奖励模块。其余约束照常。
- **支线对手和唯一件持有者**（`docs/campaign-direction.md` §6、§7）：单独一档目标，暂定"本档 Boss 打它胜率 30%～40%"；唯一件按 §7.6 的奖励车规则检查它确实有作用。解锁顺序以 `docs/campaign-direction.md` 为方向，以 `SA.CAMPAIGN` 的实际数据为准。
- **种群的三个来源**：
  1. 上一档幸存者的复制品，放宽约束后加入新模块、升级项和更大的格子；
  2. 一小批新生成的车（暂定占 20%），防止所有车都出自同一个祖先；
  3. 奖励车种子：本章每个带模块奖励的关，生成一批强制装着该模块的车。

### 7.2 合法性与"改进"操作

- **合法**：有底盘、锅炉、水箱、武器、驾驶舱；所有模块连到底盘；不超重；动力够；直射武器不被己方挡死；通过 `SA.V.issues` 和 `stats().canDeploy`。
- **改进操作**：加模块（合法位置）、删模块、换模块、挪位置、升材料、改侧挂层，以及可选的"两台车交换一组部件"。
- 改完不合法的，先尝试修补（比如动力不够就补锅炉、热量不够就补冷却），修不好就丢弃。
- 预算用 `SA.cellValue` 求和计算；Boss 和奖励车的预算上限可以放宽（暂定 ×1.3）。

### 7.3 特征与分类存档

**分类维度**（暂定）：打法 × 底盘 × 场地专长。
- **打法**：按主要伤害来源分为近战撞击、直射远程、高抛、升温、牵引，由构成和实战伤害占比一起判断。
- **底盘**：履带、四足、双足。
- **场地专长**：平地、货箱、泥地、土坡、工厂后院、矿坑。

**规则**：
- 每格保留前 3 名（暂定），同格的车只和同格竞争位置。
- 格内排名用**综合分 = 标准化强度分 + 表现分 × 权重**。表现分权重写在配置文件里，默认值让"表现分每高 10 分"约等于"强度分高一个置信区间宽度"（暂定）。
- **性格绑定**：每台车用冲锋、风筝、龟缩、游走各测一遍，绑定表现最好的那种，存进车的 `style`。

### 7.4 奇特存档与毒瘤存档

- **奇特构筑**：特征明显偏离本格常规（离格中心最远的 5%，暂定）、强度分不低于本档中位数的车。单独存档，不和常规车抢格子，选关时可以用。
- **毒瘤车**：强度分在本档前 20%、表现分低于 35 的车（暂定）。单独存档，**不用于关卡**，但完整保留，在报告页里能看到它的样子、分享码和最典型的一局。

### 7.5 地形特化

- **地形专长值** = 某地形上的强度分 − 平地上的强度分。
- **地形关的对手**（普通关）必须满足：
  - 在主场地形上，强度分落在目标区间；
  - 专长值超过门槛（暂定：大于一个置信区间宽度）；
  - 在主场的"利用地形"表现分高于本档中位数。
- **Boss 不用地形特化车**（§7.7）。Boss 关照常有场地，但 Boss 本身按通用型挑选。

### 7.6 奖励车

给模块奖励的关，敌车必须满足：

1. **装着这件奖励模块。**
2. **强度下限（已定）**：打低一档参考车（上一档 Boss）胜率 ≥ 60%，也就是低一档配置的玩家打它 ≤ 40%。
3. **生效门槛**（证明模块确实有作用）：
   - 生效统计（开火、命中、牵引、储能释放、省水等）的平均次数过门槛；
   - **对照测试**：把奖励模块换成同尺寸的甲片或装甲，胜率至少下降 10 个百分点（暂定）。
4. **防碾压上限（已定）**：上一档 Boss 打它的胜率不低于 15%。

### 7.7 Boss：本档的标杆

Boss 就是参考车。每一档先定出 Boss，再用它来衡量这一档的其他关卡。

- **候选**：从主存档里挑，不从奇特存档和毒瘤存档里挑；地形专长值低于门槛（通用型）；表现分不低于本档中位数。
- **条件（已定）**：
  - 对本档种群的平均胜率 ≥ 50%。计算时排除携带下一档新模块的奖励车，Boss 打不过它们是正常的；
  - 反过来，用本档配置的玩家打它，胜率 ≤ 50%。
- **条件（沿用 `game-design.md` §5）**：上一档 Boss 打它的胜率 < 30%。
- **不要太碾压**：在满足条件的候选里，优先选平均胜率最接近 55% 的（暂定），避免 Boss 远远强过本档所有车。
- Boss 关给模块奖励时，Boss 同样要装着这件模块，并满足 §7.6 的生效门槛。
- Boss 选定后，它就是本档的标尺车（§5），也是下一档奖励车的"低一档参考车"。

## 8. 关卡规格与选关

### 8.1 关卡规格

每一关一份规格，放在 `SA.CAMPAIGN` 的关卡数据里（字段名由 astra 定，比如 `spec`）。它是设计意图，规则变了也不作废。

- 地形；
- 奖励模块（如果有）；
- 考的打法（可选，比如"泥地里的冲锋撞击车"）；
- 目标强度区间；
- 表现分下限；
- 用户手写的名字、剧情和弱点（原样保留，算法不改）。

### 8.2 选关

- **硬条件**：满足规格里的地形、奖励模块和本关约束（Boss 和奖励车按 §7.1 例外）；表现分过线；不是毒瘤车。
- **目标强度**（"本章参考车"就是本章 Boss）：
  - 普通关：本章 Boss 打它胜率约 70%，也就是比 Boss 弱一截；
  - 地形关：在主场地形上满足同样的目标，外加 §7.5；
  - 奖励车：满足 §7.6；
  - Boss 关：按 §7.7 选出的 Boss。
- **同一章里尽量不重复打法。**
- **弱点复核**：用户手写的弱点如果能机器检查（比如"没有顶甲""水只够 40 秒"），新车不满足时在报告里标红。

### 8.3 导出

- 生成一个补丁，只替换关卡车相关字段：`rows`、`subs`、`sides`、`mt`、`elite`、`style`、`terrain`。关卡名、`pilot`、`blurb`、`unlock`、`prize` 一律不动。
- 用户在报告页确认后再应用到 `js/content.js`，并单独提交。
- 候选车库另存为 `tools/evolve-candidates.json` 进仓库，只存车的分享码、标签、分数和规则指纹，大小上限 1 MB。

## 9. 报告页

新建开发工具页 `tools/evolve.html`，挂进开发者面板（`js/camp.js` 的 `DEV_TOOLS`）。它是开发工具，直接复用现有的整车预览和试驾场，不需要新的视觉设计。

- 每一档的分类网格：每格显示缩略图、强度分、表现分、绑定的性格；
- 强度分 × 表现分散点图，毒瘤车和奇特构筑用不同标记；
- 点开一台车：大图、属性、分享码（一键复制）、典型对局的结局和种子；**直接在试驾场和它打一场**；**按种子复现某一局**；
- 选关结果和导出补丁的预览；
- 规则指纹不一致时，显示"数据过期，需要复核"。

## 10. 规则变化的处理

战斗规则以后还会改，比如反震伤害、各底盘移动时的散布差异。生成出来的车不是成品，而是"当前规则下的解"，所以要让重算便宜、可靠。

1. **关卡规格是权威**（§8.1）。规则变了，规格不动，重新求解。
2. **规则指纹**（§3.5）：指纹变了，报告页和开发者面板提示关卡车需要复核。
3. **复核和影响报告**：
   - 规则变动后，先用新规则重新评估现有关卡车和存档车（只评估，不进化）；
   - 输出每关胜率、结局分布、每件模块价值的变化；
   - 偏移超过门槛的，警告并列出。
   - 这一步接进任务 F 的自动化检查：凡是改到战斗规则的 `sys:` 提交，自动出一份影响报告。
4. **只重跑超标的部分**：以旧存档为起点重跑那几个格子或那几档，不从头进化。
5. **战斗规则冻结点**：大的机制改动集中做完之前，只跑系统健康测试和快速评估。冻结条件（暂定）：
   - 真双足（任务 E）完成；
   - 用户计划的战斗手感调整（反震、各底盘散布等）完成；
   - 用户宣布冻结。
   冻结后规则仍然可以改，只是每次都走 1～4 的流程。
6. **稳健性**：评估候选车时，把最可能被改的参数（后坐、晃动、散布、反震）各上下浮动约 10%。选关时优先选浮动下依然合格的车。

## 11. 代理 AI 校准

模拟里代替玩家的是 AI，它和真人打法不同。用少量真人对局来校准它，而不是大量游玩测试。

- **记录真人对局**：用户正常玩的时候，游戏在本机记下每局摘要，和 §3.4 同一套统计（命中率、蓄满率、交战距离、热量控制、用时、结局）。可以导出成 JSON。
- **校准**：调代理 AI 的瞄准误差、反应时间、开火节奏和热量控制，让它的统计接近用户的。每次校准十几局就够。
- **一键评价**：每局结束后可以点"好玩 / 无聊 / 不公平"，用来校准表现分的权重。按钮本身属于 UX，交给 Opus（`docs/collab.md` §7 交接板）；数据记录归 astra。

## 12. 存储上限

- **真人对局记录**：只存每局摘要（约 1～2 KB），不存逐帧数据；只保留最近 200 局，滚动覆盖；总量不超过 1 MB，存在 localStorage。导出时才写成文件。
- **进化运行的输出**：
  - 放在 `tools/out/`，加入 `.gitignore`，不进仓库；
  - 每次运行只保存存档车、汇总统计和少量典型对局的种子，**不保存逐局日志和逐帧数据**；
  - 复现靠种子重算，不靠录像；
  - 每次运行不超过 20 MB；只保留最近 3 次，更早的自动删除；目录总量不超过 100 MB。
- **进仓库的**：只有 `tools/evolve-candidates.json`（≤ 1 MB）和导出到 `js/content.js` 的关卡车。

## 13. astra 的自主权限与汇报

**可以自己决定、直接做的**：
- 跑部分实验、小规模试跑；
- 发现算法收敛离谱时，修改**算法内部**：变异操作和概率、选择压力、分格方式、采样局数、表现分各项的具体计算方式、搜索策略。
  离谱的例子：单一构筑占满大部分格子、某个模块从不出现、表现分被钻了空子、毒瘤车泛滥、强度分不收敛。
- 调整标"暂定"的数值。

**要求**：每次这类修改都写进 §15 的问题记录，写清现象、原因、改了什么、改前和改后的对比数据，并在汇报里说明。

**必须先问用户的**：
- 改战斗规则或游戏数值（包括系统健康测试推荐的数值）；
- 改标"已定"的参数；
- 改关卡规格、删功能。

**发现游戏本身的缺陷或漏洞**（比如进化找到了不合理的必胜打法）：
- 记进 §15，附上复现用的分享码和种子，并汇报；
- 明显是 bug 的可以直接修；属于设计取舍的，写成提议，等用户决定。
